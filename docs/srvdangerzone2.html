🚧 srv_normal / check0 / check1 / block

Скільки триває небезпечна зона

Емпіричний вимір каскаду srv_* у scan-detector: після правки srv_block (замість самосуперечливого правила) і переходу srv_normal на ковзне вікно (update замість add), блокування можливе лише в проміжку між тим, як «згасне» normal, і тим, як згасне check1. Нижче — де саме ця зона починається і закінчується для різних значень check1, наскільки чутливий поріг «сплеску» check0, наскільки швидко взагалі можна влучити в блок як f(normal), і як поводиться сам block — продовжується під час повторних спроб чи згасає. Усі точки — реальні TCP-з'єднання на живому nft, не розрахунок на папері.

обрано normal = 30s обрано check0 = 10s обрано check1 = 1m30s обрано block = 1m

Небезпечна зона = check1 − normal

Дев'ять значень check1, від 35s (зона 5s) до 180s (зона 150s) — суцільна лінійна крива, без винятків. Зелена ділянка [0…30s] — безпечно (перевірено паузою 25s). Заштрихована червона ділянка — небезпечна зона: пауза десь усередині неї (позначена крапкою) реально призводила до srv_block. Ширина зони не залежала від check0 — перевірено окремо на трьох його значеннях (10s / 20s / 30s), результат ідентичний у всіх випадках.

безпечна ділянка (0–30s) небезпечна зона тест-точка: не заблоковано тест-точка: заблоковано

Поріг «сплеску»: коли check0 вважає два з'єднання одним заходом

Два TCP-з'єднання з паузою GAP між ними; чи потрапляє джерело в srv_check1, залежить лише від того, чи встиг протухнути srv_check0 — тобто чи GAP < check0. Монотонний поріг, без сюрпризів, і саме тому check0 не впливає на ширину зони вище — він лише вирішує, кого туди взагалі пускають.

Мінімальний час до блоку — f(normal)

Найшвидший спосіб навмисно влучити в srv_block: сплеск (2 з'єднання з гепом 1s) і одна спроба одразу після того, як normal щойно протух. Результат ідентичний для check0 = 5s / 10s / 20s (тому на графіку — одна лінія): час до блоку = normal + 3s, лінійно, без винятків.

Поведінка block: продовження й згасання

Для кожного значення block: спершу навмисно ловимо блок, потім 3 повторні спроби з кроком block/3 (кожна мала б продовжувати блок через update), потім тиша block + 2s без жодних спроб. Довжина смуги пропорційна власній тривалості кожного рядка — шкали різні (15s і 120s поруч на одній осі були б нечитабельні).

до першого влучення заблоковано (з позначками повторів) тиша → природне згасання

Чинні правила { 80, 443 }

Точний вивід scan-detect-tool --show | grep "{ 80, 443 }" для рекомендованої конфігурації нижче.

tcp dport { 80, 443 } ct state new ip saddr != @srv_block ip saddr != @srv_normal ip saddr @srv_check1 add @srv_block { ip saddr } counter
tcp dport { 80, 443 } ct state new ip saddr != @srv_check1 ip saddr @srv_check0 add @srv_check1 { ip saddr } counter
tcp dport { 80, 443 } ct state new ip saddr != @srv_check0 add @srv_check0 { ip saddr } counter
tcp dport { 80, 443 } ct state new ip saddr != @srv_block update @srv_normal { ip saddr } counter  ← ковзне вікно
tcp dport { 80, 443 } ct state new ip saddr @srv_block update @srv_block { ip saddr } counter drop
tcp dport { 80, 443 } ct state new ip saddr @srv_normal counter return

Підсумок

check1 = 1m30s дає зону шириною 60s — досить вузьку, щоб не чіпати звичний перегляд (гепи до 30s узагалі не сягають check1), і досить широку, щоб «сплеск + випадкова пауза на каву» не був типовим патерном. check0 = 10s лишається найтугішим порогом (лише справді швидкі довантаження сторінки рахуються сплеском). Навіть навмисно найшвидше можливе влучення в блок — не менше ніж normal + 3s ≈ 33s; а сам блок, поки джерело продовжує намагатись, стабільно продовжується (update) і згасає точно за налаштований час, щойно спроби припиняються.

Методологія: реальні TCP-з'єднання на 127.0.0.1 проти живого nft у пісочниці (не симуляція), trusted тимчасово очищено від 127.0.0.0/8 на час тестів, кожна конфігурація самоперевірена (nft list set) перед вимірюванням, щоб виключити застарілий override-файл. Дані: 9 точок на поріг check0, 9 точок на криву зони, 12 точок на мінімальний час до блоку, 4 конфігурації × (3 повтори + тиша) на поведінку block. Повна методологія й таблиці — TESTS.md у репозиторії.
