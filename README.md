# scan-detector

nftables-детектор сканування портів із прогресивним graylisting (IPv4/IPv6),
списками довіри/ігнору/перманентного блоку та окремим захистом docker-контейнерів
через `forward`-ланцюг.

Проєкту 10+ років — почалось як один невеликий bash-скрипт з `sudo nft add ...`,
виписаними вручну. Цей репозиторій — його продуктизована версія: та сама логіка
nft-правил, але з атомарним застосуванням, генерацією каскадів циклом і
живим керуванням списками без повного перестворення таблиці.

## Мета проєкту — що це НЕ є

`scan-detector` — це не файрвол і не заміна файрволу. Це детектор
**потенційного сканування портів**, який відстежує підозрілий патерн (багато
NEW-з'єднань поспіль з одного джерела) як у трафіку **до самого хоста**
(`input`), так і в **транзитному** трафіку (`forward`) — і більше нічого.

Правила ні `inet scanDetector`, ні `inet srvProtector` (окрема таблиця для
захисту протокол-груп, `srv_*` — див. "Як це працює" нижче) ніколи нічого
не `accept`-ять явно — вони лише рахують і, якщо джерело пройшло **всю**
драбину ескалації (усі 16 рівнів поспіль, `scanDetector`) чи перевищило
ліміти захищених портів (`srvProtector`), `drop`-ають його. Усе інше просто
падає крізь ланцюг далі (`counter`/`return`, без термінального вердикту) —
рішення "чи дозволений цей трафік узагалі" ухвалює **щось інше**, за межами
обох цих таблиць.

Саме для цього — дефолтні пріоритети hook'ів `input`/`forward` (`-50` для
`scanDetector`, `-51` для `srvProtector`, див. нижче): обидві таблиці
навмисно виконуються **раніше** за будь-яку іншу таблицю з правилами
доступу (типово `priority filter`, тобто `0`). Вони встигають зафіксувати
патерн сканування чи перевищення лімітів ще до того, як інша таблиця
вирішить, пропускати пакет чи ні — і їм байдуже, яким буде те рішення.

Це стосується й `extra_forward_ifaces` (нижче): цей файл додає під нагляд
обох таблиць транзитні (не-docker) інтерфейси — **тільки** в сенсі "стежити
за сканувальним патерном і лімітами захищених портів і тут теж". Він нічого не каже про те, чи МАЄ
взагалі дозволятись транзит, скажімо, з `eno0` на `vlan48` — таке рішення
("дозволити"/"заборонити" певний маршрут трафіку) належить окремим
правилам, деінде: іншій таблиці чи іншому hook'у (напр. `type filter hook
forward priority filter`, тобто звичайний `0`, де й живе "справжній"
файрвол-permit/deny).

Саме в цьому й перевага такої ієрархії пріоритетів у `nftables` — розділення
відповідальності без явних залежностей: там, де вирішується, який транзитний
трафік дозволений, а який ні, зовсім не треба перейматись логікою детекції
сканування — вона вже відпрацювала раніше, на своєму окремому пріоритеті, і
жодним чином не заважає (і не залежить від) рішень permit/deny-таблиці.

## Історія

Ідея спершу підглянута в прикладах правил для MikroTik RouterOS — там здавна
є класичний рецепт градуйованого захисту SSH від брутфорсу через
`address-list` з кількома таймаутами (спроба → підозра → блок). Звідси й теза,
яку варто повторювати частіше: RouterOS — це, по суті, Linux у гарній
обгортці 😉.

Перша власна реалізація цієї ідеї була значно вужчою: `iptables` + `ipset`,
і лише для захисту SSH від брутфорсу — без градації на 16 рівнів, без
docker-інтеграції, без IPv6.

Поточна версія на `nftables` — саме той скрипт, з якого зроблено цей
репозиторій — є прямим нащадком логіки, яку було побудовано приблизно 10
років тому, тобто невдовзі після того, як у `nftables` взагалі з'явились
dynamic-сети з `timeout` (~2014–2015). Просто раніше скрипт був простим,
прямолінійним і не таким "розумним" — цього й не вимагалося, він
експлуатувався приватно, проте розвивався усі ці роки. Як окремий
публічний проєкт до моменту повного рефакторингу та переусвідомлення
нюансів не оформлювався.

## Компоненти

| Файл | Призначення |
|---|---|
| `src/bash/nft-scan-detector` | (Пере)генерує весь ruleset ОБОХ таблиць -- `inet scanDetector` (драбина level*/scan) і `inet srvProtector` (захист протокол-груп, srv_*) -- і застосовує атомарно (`nft -c -f` → `nft -f`). Викликається один раз при старті системи. |
| `src/bash/scan-detect-tool` | CLI для живого керування списками `trusted` / `ignore` / `permanentBlock` (додати, видалити, показати) — без перестворення таблиці. |
| `src/bash/docker-network-watch` | Слухає `docker events` і рестартує `scan-detector.service` при появі/зникненні docker-мережі. Опційний компонент — див. розділ нижче. |
| `src/bash/common.sh` | Спільна бібліотека обох скриптів: назви таблиць, виявлення додаткових srv-таблиць, валідація адрес. Не виконується сама, лише `source`. Встановлюється в `/usr/local/lib/nft-scandetect/`. |

Обидва скрипти вважають файли в `/etc/nft-scandetect/*.list` єдиним джерелом
правди для цих трьох списків (докладніше — нижче).

## Вимоги

- Linux з `nftables` (утиліта `nft`, версія з підтримкою `flags dynamic,timeout` та JSON-виводу `-j`)
- `jq` — потрібен `scan-detect-tool` для розбору `nft -j`
- `sudo` — обидва скрипти викликають привілейовані команди через `sudo` (працює як з-під звичайного користувача з sudo-правами, так і з-під root)
- Docker — опційно; якщо `docker` відсутній у `PATH`, `nft-scan-detector` сам вмикає режим `--no-docker`: ланцюг `forward` узагалі не створюється, `input` продовжує працювати як завжди
- IPv6 — опційно; керується `/etc/nft-scandetect/ipv6` (`0`/`1`/`auto`, дефолт `auto`) і прапорцем `--no-ipv6` — див. розділ нижче
- `ip` (пакет `iproute2`) — опційно; потрібен лише для точнішого автовизначення живого IPv6 (перевірка реальної адреси, не тільки sysctl). Без нього автовизначення спирається лише на `net.ipv6.conf.*.disable_ipv6`

## Встановлення

```sh
# Спільна бібліотека -- ОБОВ'ЯЗКОВО, обидва скрипти без неї не стартують
sudo install -D -m 644 src/bash/common.sh /usr/local/lib/nft-scandetect/common.sh

sudo install -m 755 src/bash/nft-scan-detector /usr/local/sbin/nft-scan-detector
sudo install -m 755 src/bash/scan-detect-tool  /usr/local/sbin/scan-detect-tool

sudo install -m 644 systemd/scan-detector.service /etc/systemd/system/scan-detector.service
sudo systemctl daemon-reload
sudo systemctl enable --now scan-detector.service
```

`common.sh` — не опційна дрібниця: у ній живе те, що ОБИДВА скрипти
зобов'язані бачити однаково (назви таблиць, перелік додаткових
srv-таблиць, правила валідації адрес). Якщо файл відсутній, скрипт
одразу завершується з явною помилкою, а не працює "наполовину".
Шукається він у двох місцях по черзі: `/usr/local/lib/nft-scandetect/`
(штатне після встановлення) і поруч із самим скриптом — тому запуск
прямо з `src/bash/` у репозиторії теж працює, без установки.

Якщо раніше скрипт викликався "останньою надією" з `/etc/rc.local` — приберіть
цей виклик, тепер запуск відбувається через systemd-юніт (див. нижче), впорядкований
після Docker.

## Оновлення

```sh
git pull
sudo install -D -m 644 src/bash/common.sh /usr/local/lib/nft-scandetect/common.sh
sudo install -m 755 src/bash/nft-scan-detector /usr/local/sbin/nft-scan-detector
sudo install -m 755 src/bash/scan-detect-tool  /usr/local/sbin/scan-detect-tool
sudo systemctl restart scan-detector.service
```

**Оновлюйте `common.sh` РАЗОМ зі скриптами, одним заходом.** Вона несе
спільні для обох скриптів визначення, тож стара бібліотека з новими
скриптами (чи навпаки) — це рівно та розсинхронізація, заради усунення
якої її й виділяли. Пропущений `common.sh` при першому оновленні на цю
версію — найімовірніша причина `Помилка: не знайдено common.sh`.

**Важливо: останній рядок — `restart`, не `enable --now` і не `daemon-reload`.**
Якщо `scan-detector.service` вже enabled і активний (типовий випадок після
першого встановлення), `systemctl enable --now` на вже активному юніті —
no-op: `start` на unit, який вже `active`, нічого не робить, ExecStart
повторно не виконується. `daemon-reload` теж не рестартовує сам процес —
він тільки перечитує визначення юніта. Тобто нову версію скрипта на диску
жоден з цих двох викликів не підхопить — потрібен саме явний `restart`.
(`enable --now` лишається правильною командою тільки для першого
встановлення, коли юніта ще нема.)

## Взаємодія з `nftables.service`

Якщо на хості окремо є системний `nftables.service` (типово на Debian/Ubuntu,
керує `/etc/nftables.conf`) — його старт/рестарт зазвичай виконує `flush
ruleset` і накочує лише той файл, стираючи **весь** живий ruleset, включно з
`inet scanDetector` і `inet srvProtector` обома. Це не залежить від override-файлів чи стану
`scan-detector.service` — воно просто зникає з ядра при будь-якому
`systemctl restart nftables.service`, і застосується знову лише після
наступного `systemctl restart scan-detector.service`.

Це пом'якшено двома речами:
- `scan-detector.service` тепер впорядкований `After=nftables.service` —
  на старті системи наша таблиця гарантовано застосовується вже після
  того, як `nftables.conf` накотився, а не в гонці з ним;
- опційний drop-in `systemd/nftables.service.d/restart-scan-detector.conf`
  — двома хуками навколо `nftables.service`:
  - `ExecStartPre=` — знімає live-стан каскаду (scan/level\*/srv_\*) в
    `/var/lib/nft-scandetect/live-state-pending.tsv` і видаляє ОБИДВІ наші
    таблиці **ще до** того, як `flush ruleset` зробить це сам (той самий
    шлях, що й `nft-scan-detector --stop`). Без цього кроку знімати після
    `flush` було б уже нічого;
  - `ExecStartPost=` — рестартує `scan-detector.service` вже після
    `flush`; той підхоплює відкладений знімок і відновлює обидва каскади.

  Разом ці два хуки і дають "рестарт нічого не коштує" — без `ExecStartPre`
  (як було раніше) знімати на момент `ExecStartPost` уже нема звідки: живий
  стан втрачається мовчки. Встановлюється окремо, лише якщо
  `nftables.service` реально є на хості:

```sh
sudo install -D -m 644 systemd/nftables.service.d/restart-scan-detector.conf \
    /etc/systemd/system/nftables.service.d/restart-scan-detector.conf
sudo systemctl daemon-reload
```

## Як це працює

Захист побудований на ДВОХ окремих `table inet`, кожна зі своєю ідеєю і
своїм пріоритетом hook'а — не одна велика таблиця з усім разом:

- **`srvProtector`** (пріоритет N−1, спрацьовує ПЕРШИМ) — швидкий бар'єр
  для захищених сервіс-портів (за замовчуванням tcp/80, tcp/443; перелік і
  ліміти конфігуруються, див. нижче), на базі нативних `nftables meter`:
  `limit rate` (token bucket — скільки нових з'єднань за час, з дозволеним
  сплеском) і `ct count` (скільки одночасно відкритих з'єднань).
- **`scanDetector`** (пріоритет N, спрацьовує ДРУГИМ) — повільніша, довга
  (до 31 дня) драбина ескалації `level*`/`scan` для будь-якого сканування,
  незалежно від порту.

Обидві прикріплені до тих самих hook'ів (`input`, і `forward` окремо для
кожного docker bridge) — netfilter проганяє пакет крізь них по черзі, за
пріоритетом (менше число — раніше). `drop` у будь-якій з них одразу й
остаточно припиняє обробку пакета всюди (він не "провалюється" в наступну
таблицю); якщо жодна не дропнула — пакет проходить усі.

Це дефолт із двох таблиць, але їх може бути й більше: понад `srvProtector`
можна додати ДОВІЛЬНУ кількість ще таких самих "protector"-подібних
таблиць — кожна свій підкаталог `/etc/nft-scandetect/<назва>/`, свій набір
захищених портів і лімітів, свій (нижчий за `scanDetector`) пріоритет —
див. "Назва nft-таблиць" нижче.

Тобто: одне нове з'єднання само по собі нічого не блокує — адреса лише потрапляє
на `level15` (найкоротший таймаут). Але якщо джерело продовжує відкривати нові
з'єднання швидше, ніж встигає спливти таймаут поточного рівня, воно щоразу
"падає" на рівень нижче (з довшим таймаутом), і врешті потрапляє в `scan` —
звідти дропається на 31 день. Якщо ж пауза між спробами достатня — рівень
просто протухає сам, без жодного блокування.

Перевищення `rate` чи `over` у `srvProtector` одразу веде в `srv_block`
(окремий, короткий блок — типово 1 хвилина, не 31 день), ще до того, як
джерело встигне докотитись до `scanDetector` взагалі.

Уся ця послідовність продубльована:
- для `input` (трафік на сам хост) і для кожного docker bridge в `forward`
  (трафік ззовні до контейнерів) — в ОБОХ таблицях;
- окремо для IPv4 (`trusted`, `ignore`, `permanentBlock`, `level0..N`, `scan`)
  і IPv6 (`trusted6`, `ignore6`, `permanentBlock6`, `level6_0..N`, `scan6`) —
  `N` за замовчуванням 15 (16 рівнів), теж конфігурується.

### Два входи в драбину: звичайні з'єднання і stealth-скани

Каскад `level*`/`scan` живе в окремому ланцюзі (`cascade_input`/
`cascade_forward` і їх v6-відповідники), і потрапити в нього можна ДВОМА
шляхами:

1. **`ct state new`** — звичайне нове з'єднання. Класичний шлях, як і всі
   ці роки.
2. **`ct state invalid` + аномальні TCP-прапорці** — те, чим працюють
   `nmap -sN` (NULL), `-sF` (FIN) і `-sX` (XMAS). Такий пакет НІКОЛИ не
   має стану `new`: conntrack (з дефолтним `nf_conntrack_tcp_loose=1`)
   бачить його як `invalid`, тож до цієї зміни драбина його просто **не
   бачила** — stealth-скан проходив крізь детектор повністю невидимим.
   Перевірено наживо, разом із рештою типів сканів — див.
   [TESTS.md](TESTS.md).

ACK-скан (`nmap -sA`) окремого входу не потребує: conntrack трактує його
як `new`, і драбина ловила його й раніше.

Умова `ct state invalid` тут обов'язкова саме тому, що сам по собі матч на
одинокий `fin` зачепив би й легітимне закриття з'єднання; `invalid` звужує
його рівно до пакетів, яких conntrack не зміг віднести до жодного потоку.
Перевірено окремим тестом: десяток нормальних TCP-сесій із штатним
закриттям лишає лічильники stealth-правил на нулі.

Stealth-пакет заходить у ту саму драбину на загальних підставах — з
найм'якшого рівня, з тією самою ескалацією. Одинокий "заблуканий" пакет
(асиметричний роутинг, переповнення conntrack) нічого не блокує; скан на
десятки портів проходить рівні так само, як і будь-який інший.

Нюанс #1 (успадкований від часів однієї таблиці): `srv_block`/`srv6_block`
(сет) — спільний для `input` і всіх `forward`-бриджів разом у
`srvProtector`, той самий "хто вже спійманий" список скрізь. А
`meter`-лічильники `rate`/`over` — **не** спільні: nftables не дозволяє
повторно використати те саме ім'я `meter` у двох різних правилах, тож
кожна (chain × bridge × протокол-група з `srv_ports`) комбінація отримує
свій незалежний бюджет. Джерело, що б'є одразу по кількох bridge, має
окремий ліміт на кожен. Для типової інсталяції (один bridge чи
`--no-docker`) різниці нема. Каскад `level*`/`scan` цього нюансу не має —
там усе, як і раніше, звичайні сети, спільні для всього.

Нюанс #0 (про структуру, не про логіку): у `forward` base chain лежить
рівно ОДНЕ правило — `oifname vmap { "br-a" : jump fwd_0, ... }`. Кожен
bridge має власний ланцюг `fwd_N`, а сам каскад `level*`/`scan` — один
спільний на весь hook. Раніше правила всіх бриджів лежали в base chain
поспіль, кожне з префіксом `iifname != X oifname X`, і пакет для другого
бриджа спершу марно перебирав усі правила першого:

| Бриджів | Правил у `forward` (було → стало) |
|---|---|
| 2 | ~44 → 1 (+ 2×10 у `fwd_N`, + 18 спільний каскад) |
| 10 | ~220 → 1 (+ 10×10, + 18) |

`vmap` — це хеш-lookup за O(1) незалежно від кількості бриджів, тож
глибина проходу на пакет більше не росте з кожною новою docker-мережею.
Поведінка й лог-префікси (`scandetect-forward-drop` тощо) — ідентичні;
перевірено наживо, включно з `--stop-fwd`, який тепер прибирає й ці
допоміжні ланцюги.

Нюанс #2 (новий, від розділення на дві таблиці): `trusted`/`ignore`/
`permanentBlock` (і v6-варіанти) — сети ДУБЛЬОВАНІ, з ІДЕНТИЧНИМ вмістом,
в ОБОХ таблицях. Причина проста: `return` у `trusted`/`ignore` виходить
лише з ВЛАСНОГО chain своєї таблиці, а не пропускає другу таблицю на тому
самому hook'у (nftables не має "пропустити решту таблиць на hook'у" —
лише "пропустити решту правил цього chain"), тож кожна таблиця мусить сама
собі перевіряти "чи довірений", а не покладатись на сусідню. Джерело
правди для обох лишається те саме (`*-extra.list` override-файли) —
`scan-detect-tool --add-trusted`/`--add-ignore`/`--add-permanent`
застосовує зміну одразу в обидві таблиці (див. нижче), щоб вони не
розійшлись.

## Прапорці `nft-scan-detector`

Сім прапорців, двох різних видів:

- **Модифікатори звичайної генерації** — `--reset-live-state`, `--no-docker`
  і `--no-ipv6`. Незалежні один від одного й вільно комбінуються в
  будь-якому порядку — кожен впливає на свою частину ruleset і не
  залежить від інших.
- **Окремі режими** — `--stop-fwd`, `--stop-fwd-docker`, `--stop`, `--init`.
  Кожен нічого не генерує, робить рівно одну дію і виходить; взаємовиключні
  і між собою, і з трьома модифікаторами вище (бо генерації, яку можна
  було б модифікувати, в цих режимах просто нема).

### `--reset-live-state`

`nft-scan-detector` завжди перестворює ОБИДВІ таблиці (`delete table` +
`add table`, кожну окремо) — так було і в оригінальному скрипті 10 років
тому (тоді, звісно, з однією таблицею). Але тепер це більше не означає
втрату прогресу: перед перестворенням береться знімок поточних елементів
усіх dynamic-сетів (`scan`, `level0..level15` з `scanDetector`, `srv_block`
з `srvProtector`, і їхніх IPv6-відповідників) разом із рештою таймауту, і
одразу після перестворення сетів цей знімок відновлюється в КОЖНІЙ
таблиці — в тій самій nft-транзакції (`nft -c -f` перевіряє й дамп, і
відновлення разом з рештою ruleset).
`srv_rl_N`/`srv_over_N` (`meter`) у цей знімок не потрапляють: знімок бере
лише елементи з `flags timeout`, а в `meter` — `flags dynamic` без
`timeout` (він і не має "спадати" сам, на відміну від `srv_block`/рівнів).
Тож ці лічильники завжди стартують "з нуля" після кожного перестворення
(`srv_block` — ні). Нюанс версій `nft`: як саме `nft -j list` віддає
`meter` (під ключем `"meter"` чи як звичайний `"set"` з `flags dynamic`)
залежить від версії — і не важливо для цього фільтра, бо той дивиться на
`flags timeout`, якого в `meter` нема в жодній версії.
Знімок також зберігається в `/var/lib/nft-scandetect/live-state-<ts>.tsv` —
поруч з аудитом самого ruleset (`ruleset-<ts>.nft`).

**Ротація аудиту.** Обидва ці файли пишуться на КОЖНОМУ запуску, а з
`docker-network-watch` запусків буває помітно більше, ніж здається (кожна
поява/зникнення docker-мережі — рестарт сервісу). Тому файли, старші за
`AUDIT_RETENTION_DAYS` (за замовчуванням **14 днів**, константа на початку
`nft-scan-detector`), прибираються наприкінці кожного успішного запуску.
`live-state-pending.tsv` під ротацію не потрапляє ніколи — він не має
мітки часу й не застаріває за розкладом, його споживає наступний запуск.
Поставте `0`, щоб вимкнути ротацію зовсім.

**Вивід у журнал.** Повний дамп таблиць скрипт друкує лише коли його
запустили руками (є tty). Під systemd stdout іде в journal, а дамп — це
весь вміст `scan`/`level*`, тобто на робочому хості сотні адрес і сотні
кілобайт **на кожен рестарт**. Подивитись стан завжди можна окремо:
`scan-detect-tool --show`.

Якщо потрібна стара поведінка (наприклад, свідомо "амністувати" всіх, хто
зараз у каскаді) — прапорець вимикає збереження, і таблиця перестворюється
з чистими сетами:

```sh
sudo nft-scan-detector --reset-live-state
```

Списки `trusted`/`ignore`/`permanentBlock` цього не стосуються — вони й так
не втрачаються, бо йдуть через override-файли (нижче), а не через live-стан
dynamic-сетів.

### `--no-docker`

Вимикає **автопідхоплення docker-бриджів** — не саму генерацію `forward`
узагалі (див. `extra_forward_ifaces` нижче). Для хостів без Docker або де
docker-мережі захищаються інакше. Вмикається і вручну, і автоматично — якщо
на хості немає бінарника `docker`, `nft-scan-detector` сам про це
попереджає в stderr і працює так, ніби прапорець передали:

```sh
sudo nft-scan-detector --no-docker
```

Сети `level*`/`scan`/`srv_*` спільні для `input` і `forward` (це той самий
IP-рівень graylisting), тож `--no-docker` ніяк не заважає `--reset-live-state`
і навпаки — наприклад, `--reset-live-state --no-docker` разом скидає live-стан
і водночас не підхоплює docker-бриджі.

### `/etc/nft-scandetect/extra_forward_ifaces` — транзит через не-docker інтерфейси

Список інтерфейсів для `forward` за замовчуванням повністю походить від
docker-бриджів (`docker network ls`/`inspect`). Якщо потрібно відстежувати
сканувальний патерн і в транзитному трафіку через **фізичні (не-docker)
інтерфейси** — наприклад, хост маршрутизує між `eno0` і `eno1` без жодного
Docker узагалі — по одному імені інтерфейса на рядок:

```
# /etc/nft-scandetect/extra_forward_ifaces
eno0
eno1
```

Кожен інтерфейс звідси отримує **ідентичні** forward-правила, що й
docker-бридж — та сама побудова `iifname != IFACE oifname IFACE` (див.
"Мета проєкту" вище: це тільки детекція сканування, не permit/deny транзиту
як такого). Неіснуючий інтерфейс (`ip link show` не знаходить) —
попередження в stderr і пропуск, решта застосовується. Порожньо за
замовчуванням; файл засівається `--init`/першим запуском із коментарями,
але сам список — тільки вручну, `scan-detect-tool` ним не керує.

Ланцюг `forward` тепер будується, якщо є **хоч один** інтерфейс — з Docker
(якщо не `--no-docker`) чи з цього файлу. Зокрема, `--no-docker` разом з
непорожнім `extra_forward_ifaces` цілком коректно дає `forward` тільки для
перелічених там фізичних інтерфейсів, без жодної залежності від Docker.

### `--no-ipv6` та `/etc/nft-scandetect/ipv6`

Не генерує жодних v6-сетів і v6-правил: `trusted6`, `ignore6`,
`permanentBlock6`, `level6_*`, `srv6_*`, `scan6`, і всі `ip6`-рядки в
`input` і в кожному `forward`. Для хостів, де IPv6 фактично не працює —
нема сенсу тримати мертві сети й правила, які ніколи ні на що не
спрацюють.

Два способи керування, у порядку пріоритету:

1. **`--no-ipv6`** (прапорець) — разовий force-off для цього запуску,
   переважає все нижче:

   ```sh
   sudo nft-scan-detector --no-ipv6
   ```

2. **`/etc/nft-scandetect/ipv6`** — постійне налаштування, якщо прапорця
   не було. Рівно одне слово, дефолт `auto`:

   | Значення | Дія |
   |---|---|
   | `0` / `off` | завжди вимкнено (як `--no-ipv6`, але постійно, без прапорця) |
   | `1` / `on` | завжди увімкнено, незалежно від sysctl чи наявних адрес |
   | `auto` | автовизначення (нижче) |

`auto` вмикає v6-ruleset, лише якщо **обидві** умови виконані: IPv6 не
вимкнено системно (`net.ipv6.conf.all.disable_ipv6=0`, чи взагалі відсутній
`/proc/sys/net/ipv6` — тоді вимкнено) **і** десь на хості реально є
маршрутизована (не link-local) IPv6-адреса — `ip -6 -o addr show scope
global`, перевіряється на **всіх** інтерфейсах, включно з `lo` (там теж
трапляються "білі" адреси). Сам `disable_ipv6=0` — занадто слабкий сигнал:
це стан практично будь-якого інтерфейса за замовчуванням, включно з
щойно створеним docker-бриджем, а не доказ реальної IPv6-звʼязності.
Якщо `ip` немає в системі — перевірити адреси нічим, довіряємось лише
sysctl (як було раніше).

Незалежно від глобального рішення, **для кожного docker bridge окремо**
`forward`-правила для `ip6` пропускаються, якщо саме на цьому bridge
IPv6 вимкнено (`net.ipv6.conf.<bridge>.disable_ipv6=1`) — навіть коли
глобально IPv6 живий. Це **навмисно простіша** перевірка, ніж глобальна
(лише sysctl, без вимоги реальної адреси на самому bridge) — топологій
транзиту трафіку до контейнерів забагато, щоб бути тут категоричними;
хибний "вимкнено" був би дірою в захисті, а хибний "увімкнено" — просто
зайвим (нешкідливим) правилом. Якщо потрібна точніша поведінка для
конкретного bridge — `net.ipv6.conf.<bridge>.disable_ipv6` виставляється
вручну, скрипт це вже враховує. `input` — виняток: це не per-interface
ланцюг, тож там рішення лише глобальне.

### `--stop-fwd` / `--stop-fwd-docker`

Окремий режим — нічого не перегенеровує, лише знімає ланцюг `forward` із
ОБОХ **живих** таблиць (`input`, усі сети й live-стан не чіпає в жодній).
Взаємовиключний з `--reset-live-state`/`--no-docker` (це прапорці
генерації, а окремі режими її взагалі не запускають).

Навіщо: `forward` із великою кількістю per-bridge правил (16 рівнів × dual
stack × кожен bridge) заважає Docker чисто "гаситись" — daemon під час
зупинки посилає купу netlink-подій на видалення бриджів/veth, і активний
hook на `forward` це лише сповільнює. `--stop-fwd` знімає цей hook заздалегідь:

```sh
sudo nft-scan-detector --stop-fwd            # тільки зняти forward
sudo nft-scan-detector --stop-fwd-docker     # зняти forward + systemctl stop docker.socket docker.service
```

`--stop-fwd-docker` зупиняє спершу `docker.socket`, потім `docker.service`
(у цьому порядку — інакше socket-activation підніме `docker.service` назад
щойно хтось звернеться до сокета). Щоб повернути `forward` — достатньо
звичайного запуску `nft-scan-detector` (без окремих режимів) після того, як
Docker знову працює.

### `--stop`

Ще один окремий режим — прибирає ОБИДВІ таблиці (`inet scanDetector`,
`inet srvProtector`) із системи **повністю** (`delete table` для кожної): і
`input`, і `forward`, і всі сети в обох. На відміну від `--stop-fwd`, після
цього хост і docker-мережі не захищені жодним чином, а не лише в частині
`forward`:

```sh
sudo nft-scan-detector --stop
```

Live-стан каскаду (`scan`/`level*` з `scanDetector`, `srv_*` з
`srvProtector`) перед видаленням не втрачається — лягає у ЄДИНИЙ
фіксований файл `/var/lib/nft-scandetect/live-state-pending.tsv` (обидва
знімки разом).
Щоб повернути захист — звичайний запуск `nft-scan-detector` (без окремих
режимів) чи `systemctl start`/`restart scan-detector.service`: перший же
такий запуск бачить цей файл, відновлює каскад із нього (з коректно
пересчитаним рештою таймауту) і видаляє файл — одноразове споживання,
незалежно від того, скільки часу минуло між `--stop` і поверненням.
`--reset-live-state` цей файл ігнорує й прибирає теж — явний запит почати
з чистого.

Це і є `ExecStop` у `scan-detector.service`: `systemctl stop
scan-detector.service` тепер реально гасить обидві таблиці (раніше — ні: юніт
`Type=oneshot` з `RemainAfterExit=yes` без `ExecStop` на `stop` лише
позначає себе неактивним у systemd, живої nft-таблиці взагалі не чіпаючи).
`systemctl restart` (його використовують `docker-network-watch` і
drop-in на `nftables.service`) тим часом лишається безпечним — `stop`-фаза
рестарту так само сташить стан у той самий файл, а `start`-фаза одразу ж
його забирає, тож пауза між ними — мілісекунди, і жодних відчутних змін
у таймаутах не відбувається.

### `--init`

Ще один окремий режим — лише досіює відсутні override-файли в
`/etc/nft-scandetect/` вбудованими дефолтами і виходить, не чіпаючи живі
таблиці, Docker чи live-стан. Корисно, щоб проінспектувати чи заздалегідь
поправити конфіги **до** першого реального застосування таблиць:

```sh
sudo nft-scan-detector --init
# або те саме через scan-detect-tool:
sudo scan-detect-tool --init
```

Взаємовиключний з рештою прапорців. Безпечно викликати й повторно, і після
того, як таблиця вже застосована — існуючі файли не чіпає, довписує лише
те, чого справді бракує.

### Як усе це обробляється разом

Валідація, автовизначення `--no-docker`/`--no-ipv6` і фінальна
диспетчеризація — в такому порядку (1:1 з кодом, не спрощено):

```mermaid
flowchart TD
    A["Розбір CLI-аргументів"] --> B["STANDALONE_MODES = кількість увімкнених<br/>серед --stop-fwd / --stop / --init"]
    B --> C{"STANDALONE_MODES > 1?"}
    C -- так --> ERR1[["Помилка:<br/>режими взаємовиключні між собою"]]
    C -- ні --> D{"STANDALONE_MODES = 1 і передано<br/>--reset-live-state / --no-docker / --no-ipv6?"}
    D -- так --> ERR2[["Помилка: режим не можна<br/>комбінувати з модифікаторами"]]
    D -- ні --> D2{"STANDALONE_MODES = 0?"}

    D2 -- "ні (валідний --stop-fwd*/--stop/--init)" --> N
    D2 -- так --> E{"--no-docker передано?"}

    E -- ні --> F{"docker є в PATH?"}
    F -- ні --> G["NO_DOCKER = 1"]
    F -- так --> H
    E -- так --> H{"--no-ipv6 передано?"}
    G --> H

    H -- ні --> I["читає /etc/nft-scandetect/ipv6"]
    I --> J{"значення файлу?"}
    J -- "0 / off" --> K["NO_IPV6 = 1"]
    J -- "1 / on" --> L["NO_IPV6 = 0"]
    J -- auto --> M{"sysctl не вимкнено ГЛОБАЛЬНО<br/>і є хоч одна scope-global<br/>IPv6-адреса на хості (вкл. lo)?"}
    M -- так --> L
    M -- ні --> K
    H -- так --> N
    K --> N
    L --> N

    N{"Диспетчеризація"}
    N -- "--stop-fwd" --> O["do_stop_fwd<br/>(+ do_stop_docker при --stop-fwd-docker)"]
    N -- "--stop" --> P["do_stop_all<br/>(delete table повністю)"]
    N -- "--init" --> Q["do_init<br/>(лише сідінг override-файлів)"]
    N -- "жоден з трьох" --> R["main → build_ruleset:<br/>RESET_LIVE_STATE / NO_DOCKER / NO_IPV6<br/>+ окремий per-bridge IPv6-чек у forward"]
```

Один нюанс поза діаграмою: `--no-docker`/`--no-ipv6` — глобальні рішення
(на весь ruleset), а per-bridge IPv6-чек у блоці `R` — окрема, простіша
перевірка (лише `net.ipv6.conf.<bridge>.disable_ipv6`, без вимоги реальної
адреси), що виконується для **кожного** docker bridge під час генерації
`forward`, незалежно від того, що вирішив блок `H`–`M` вище.

## Пріоритет hook'ів `input`/`forward`

Дефолт — `-50` (як в оригінальному скрипті 10 років тому) для `scanDetector`.
Перевизначається файлом `/etc/nft-scandetect/priority` — **рівно одне ціле
число, без коментарів** (на відміну від `*-extra.list` файлів вище,
читається просто через `head -1`, без парсингу коментарів/порожніх рядків).
Створюється сам при першому запуску `nft-scan-detector` з дефолтним
значенням.

`srvProtector` (див. нижче) свого окремого файлу пріоритету НЕ має — його
пріоритет завжди РІВНО N−1 (де N — значення з `priority`), рахується
автоматично при кожній генерації. Це свідоме рішення, не недогляд: менше
число в nftables означає "спрацьовує раніше", і `srvProtector` мусить
відсікати джерело ДО того, як пакет дійде до `scanDetector` (той самий
ефект, що й порядок правил у межах однієї таблиці до розділення на дві) —
довільних окремих пріоритетів для нього не передбачено.

Нелегітимне значення (не ціле число) чи зіпсований файл не ламають ruleset —
`nft-scan-detector` виводить попередження в stderr і використовує дефолт `-50`
(а `srvProtector` тоді -- `-51`).

Керувати можна вручну (`echo -75 | sudo tee /etc/nft-scandetect/priority`) або
через `scan-detect-tool`:

```sh
scan-detect-tool --set-priority -75
```

На відміну від `--add-trusted`/`--add-ignore`/`--add-permanent`, це не
"живий" `add element` — пріоритет належить самому hook'у, тож застосувати
нове значення можна лише повною перегенерацією. `--set-priority` записує
файл і одразу рестартує `scan-detector.service` (якщо юніт не знайдено —
попереджає й пропонує застосувати вручну через `nft-scan-detector`) — обидві
таблиці підхоплюють новий пріоритет разом (`srvProtector` — новий N−1).
Live-стан каскаду цей рестарт переживає так само, як і будь-який інший.

## Назва nft-таблиць

Дві таблиці, дві незалежні назви:

- `/etc/nft-scandetect/table_name` — дефолт `scanDetector` (драбина
  ескалації `level*`/`scan`);
- `/etc/nft-scandetect/table_name_srv` — дефолт `srvProtector` (захист
  протокол-груп, `srv_*`).

Родина в обох — завжди `inet` (не конфігурується: потрібна для одночасних
`ip`/`ip6` правил в одній таблиці). Той самий однорядковий формат, що й
`priority` (легітимний nft-ідентифікатор: літери/цифри/підкреслення, не з
цифри) для кожного файлу окремо. Обидва створюються самі при першому
запуску `nft-scan-detector` з дефолтними значеннями. Дві назви НЕ можуть
збігатися — `nft-scan-detector` перевіряє це і відмовляється будувати
ruleset, якщо `table_name` і `table_name_srv` виявились однаковими (інакше
обидва блоки генерації намагались би керувати однією й тією ж nft-таблицею).

Нелегітимне значення чи зіпсований файл не ламають ruleset — попередження в
stderr і відповідний дефолт.

Керувати можна тільки через `scan-detect-tool` (не вручну редагуванням
файлу):

```sh
scan-detect-tool --set-table-name myScanDetector
scan-detect-tool --set-table-name-srv myProtector
```

На відміну від решти override-файлів тут недостатньо просто переписати файл
і рестартнути `scan-detector.service` — `nft` не вміє перейменувати таблицю
"на місці". Звичайний перезапуск під новою назвою створив би НОВУ таблицю
поруч зі СТАРОЮ, а стара лишилась би назавжди активною в системі й далі
фільтрувала б трафік під забутою назвою. Тож обидва сеттери (кожен для
своєї таблиці):

1. пишуть нову назву у відповідний файл;
2. прибирають стару таблицю (`nft delete table inet <стара_назва>`), якщо
   вона є;
3. рестартують `scan-detector.service`, щоб таблиця піднялась під новою
   назвою (друга таблиця регенерується разом, під своєю поточною назвою).

Live-стан ТІЄЇ таблиці, яку перейменовують, цей рестарт **не** переживає —
стара таблиця видаляється разом з ним, як і при будь-якому
`nft delete table`. Друга таблиця (яку не перейменовували) — переживає, як
і при звичайному рестарті.

### Додаткові srv-таблиці — підкаталоги `/etc/nft-scandetect/`

Понад `scanDetector`/`srvProtector` можна мати ДОВІЛЬНУ кількість ще
таких самих, protector-подібних таблиць — кожна свій підкаталог
`/etc/nft-scandetect/<назва>/`. Навіщо: коли одному набору `srv_ports`/
`srv_timeouts` на все не досить — наприклад, типові веб-порти (`tcp/80,
443`) з м'якими лімітами, і окремо `tcp/22` з жорсткішими (`rate:5/minute
burst:2 over:3`), кожен зі своєю статистикою й незалежним `srv_block`.

```sh
sudo mkdir /etc/nft-scandetect/sshProtector
echo tcp/22 | sudo tee /etc/nft-scandetect/sshProtector/srv_ports
printf 'rate:5/minute\nburst:2\nover:3\nblock:10m\n' | sudo tee /etc/nft-scandetect/sshProtector/srv_timeouts
sudo nft-scan-detector   # або systemctl restart scan-detector.service
```

Назва каталогу = назва таблиці (`table inet sshProtector` у прикладі вище)
— легітимний nft-ідентифікатор, інакше каталог пропускається з
попередженням у stderr; так само пропускається, якщо збігається з назвою
`scanDetector`/`srvProtector`. Усередині — РІВНО два файли, той самий
формат, що й у корені `/etc/nft-scandetect/`:

- `srv_ports` — які порти захищає САМЕ ця таблиця (нижче);
- `srv_timeouts` — з якими лімітами (нижче);
- `priority` — опційно, те саме ціле число, що й головний `priority`, але
  з обов'язковою умовою: МЕНШЕ за нього (гарантія перевіряється —
  нелегітимне значення чи значення, що не менше за основний `priority`,
  фолбечить на `priority-1`, той самий дефолт, що й у `srvProtector`, з
  попередженням). Без файлу — теж `priority-1`.

Усе інше — `trusted`/`ignore`/`permanentBlock` (і v6), `/etc/nft-scandetect/ipv6`,
`level_timeouts`, `extra_forward_ifaces` — своїх override-файлів у
підкаталозі НЕ мають, а УСПАДКОВУЮТЬСЯ з головного конфігу. Дублювати їх
сенсу нема (та сама довіра/ігнор має діяти скрізь однаково) — на відміну
від `srv_ports`/`srv_timeouts`/`priority`, заради яких ця додаткова
таблиця власне й існує.

Каталоги створюються й видаляються вручну (`mkdir`/`rmdir` чи
`rm -r`) — `nft-scan-detector` сам їх не створює й не прибирає, лише
досіює відсутні `srv_ports`/`srv_timeouts` всередині вже наявного
каталогу (як і для `scanDetector`/`srvProtector`) і генерує/видаляє
відповідну `table inet` при кожному regen/`--stop`. Перейменування такої
таблиці — просто перейменувати сам каталог (`mv`) і зробити звичайний
рестарт: стара таблиця під забутою назвою НЕ прибирається автоматично
(на відміну від `--set-table-name`/`--set-table-name-srv`, які саме
для цього й існують для двох головних) — приберіть її вручну
(`sudo nft delete table inet <стара_назва>`), якщо перейменовуєте.

`scan-detect-tool` бачить усі ці таблиці автоматично (той самий механізм
виявлення) — `--show`, `--add-trusted`/`--add-ignore`/`--add-permanent`,
`--list`, `--delete` враховують їх нарівні з `scanDetector`/`srvProtector`,
без окремих прапорців.

## Драбина ескалації та захищені сервіс-порти

Так само, як `priority`, ще три параметри винесені в override-файли (замість
хардкоду в скрипті) — і так само: невалідний файл ніколи не ламає ruleset,
а фолбечить на вбудований дефолт із попередженням у stderr.

### `/etc/nft-scandetect/level_timeouts` — кількість рівнів, їхні таймаути й таймаут `scan`

За замовчуванням — 16 рядків, `0:3h` .. `15:1m` (те, що й завжди було).
Формат: `N:timeout` по рядку, коментарі через `#`. Рядки мають утворювати
**суцільну послідовність від 0** — без пропусків і без дублікатів (бо каскад
`level0 → level1 → … → levelN → scan` будується саме по цій послідовності).
Кількість рядків у файлі = кількість рівнів: хочеш 20 рівнів замість 16 —
допиши `16:1m`, `17:1m`, `18:1m`, `19:1m`; хочеш 10 — прибери зайві рядки.
Той самий список таймаутів іде і на IPv4 (`level0..levelN`), і на IPv6
(`level6_0..level6_N`) — як і зараз.

Той самий файл — місце й для таймауту фінального блоку `scan`/`scan6` (куди
адреса потрапляє, "провалившись" крізь `level0`, і звідки дропається до
кінця цього таймауту): необов'язковий рядок `scan:timeout`, за замовчуванням
`scan:31d` (те, що й завжди було, просто раніше було вшите числом у код).
Якщо рядка нема — 31 день і без нього. Два `scan:` рядки одразу, чи
`scan:` не там, де очікується формат — уся конфігурація файлу (і рівні
теж) фолбечить на вбудований дефолт із попередженням.

### `/etc/nft-scandetect/srv_ports` — які порти захищає `srv_*`

За замовчуванням — `tcp/80`, `tcp/443` (те, що й завжди було, просто раніше
було вшите як `tcp dport { 80, 443 }`). Формат: `proto/port` по рядку,
`proto` — `tcp` або `udp`. Можна додати, наприклад, `udp/53`:

```
tcp/80
tcp/443
udp/53
```

Порти одного протоколу групуються в один `dport`-матч ("протокол-група").
Кожна протокол-група отримує **власний, незалежний** `meter`-бюджет
(`rate`/`over`, див. нижче) — на відміну від `srv_block`, який лишається
спільним для всіх груп разом (нативне обмеження `nftables`: іменований
`meter` не можна повторно використати у двох різних правилах, на відміну
від звичайного `set`). Невідомий рядок (не `tcp|udp/1..65535`) пропускається
з попередженням, решта застосовується.

### `/etc/nft-scandetect/srv_timeouts` — ліміти `srv_*`

Усе, що описано в цьому розділі (і `srv_ports` вище), живе в окремій
таблиці `srvProtector` (не в `scanDetector`) — див. "Як це працює" й
"Назва nft-таблиць" вище.

За замовчуванням — `rate:20/minute`, `burst:5`, `over:20`, `block:1m`.
Формат: `stage:value` по рядку, рівно ці чотири стадії, кожна один раз
(порядок рядків не важливий). Неповний набір чи зайва/невідома стадія —
фолбек на дефолт цілком (не частково).

Захист захищених портів побудований на двох нативних `nftables meter`
(per-source лічильники), а не на саморобному каскаді сетів:

- **`rate`** — `limit rate` (token bucket): скільки НОВИХ з'єднань за час
  допустимо з одного джерела (напр. `20/minute`). `burst` — скільки з них
  можна одразу підряд, понад темп `rate`, перш ніж лічильник почне
  стримувати (типовий сплеск завантаження сторінки без http2).
- **`over`** — `ct count over N`: скільки ОДНОЧАСНО відкритих з'єднань з
  одного джерела допустимо (інший сигнал — не темп нових з'єднань, а
  утримання багатьох одразу).

Перевищення БУДЬ-ЯКОГО з двох одразу веде джерело в `srv_block`
(`update` на кожній повторній спробі — не спадає передчасно, доки джерело
намагається; природно згасає за `block`, якщо спроби припиняються).

Перед цими двома `meter`-перевірками в кожній протокол-групі є ще один,
третій `permanentBlock`-рядок — той самий сет, що й на початку `input`/
`forward`, але СКОПОВАНИЙ саме на захищені порти (`tcp dport { 80, 443 }
... ip saddr @permanentBlock counter drop`). Для захисту він не потрібен
(перший, чейн-широкий `permanentBlock`-дроп уже й так термінальний і
спрацьовує раніше) — це суто для окремого лічильника: скільки трафіку від
permanent-но заблокованих джерел прицільно бив саме в захищені порти, той
самий принцип гранулярності, що й окремі копії guard-правил на кожен
forward-bridge.

Ця схема замінила попередній сетовий каскад `srv_normal`/`check0`/`check1`
(градуйована ескалація з "небезпечною зоною" між паузами) — токен-бакет
структурно не має цієї проблеми: стабільний легітимний трафік у межах
`rate` ніколи не потрапляє в блок незалежно від тривалості сесії, а
стабільний швидкий потік (який старий каскад взагалі не бачив — ковзне
вікно `srv_normal` встигало освіжатись щоразу) тепер ловиться через
`rate`. Повне порівняння обох підходів на реальних TCP-з'єднаннях,
причина заміни й усі проміжні знахідки — [TESTS.md](TESTS.md).

## Автопідхоплення docker-мереж: `docker-network-watch`

`nft-scan-detector` визначає список docker-бриджів один раз при запуску.
Якщо ти рідко, але додаєш/прибираєш docker-мережі "на живу" — щоб новий
bridge підхопився в `forward` без ручного рестарту сервісу, є окремий
слухач подій Docker: `src/bash/docker-network-watch` +
`systemd/docker-network-watch.service`.

Як це працює: скрипт підписується на `docker events --filter type=network`
(create/destroy), і на кожну таку подію викликає
`systemctl restart scan-detector.service`. Live-стан каскаду переживає цей
рестарт (див. `--reset-live-state` вище), тож рестарт нічого не коштує.
Якщо кілька мереж з'являються одна за одною (напр. `docker compose up`
одразу створює декілька) — вбудований дебаунс (2s тиші після останньої
події) згортає серію в один рестарт, а не по одному на кожну мережу.

Встановлення:

```sh
sudo install -m 755 src/bash/docker-network-watch /usr/local/sbin/docker-network-watch
sudo install -m 644 systemd/docker-network-watch.service /etc/systemd/system/docker-network-watch.service
sudo systemctl daemon-reload
sudo systemctl enable --now docker-network-watch.service
```

Юніт має `Requires=docker.service` — якщо Docker на хості явно зупинити
(зокрема через `nft-scan-detector --stop-fwd-docker`), слухач зупиниться
разом з ним, а не крутитиметься марно в `Restart=always`. Якщо на хості
взагалі немає Docker — цей юніт не потрібен, не enable-ти його.

## Списки: trusted / ignore / permanentBlock

- **trusted** — довірені джерела (напр. NOC-сервери), пропускаються (`return`) без обмежень.
- **ignore** — адреси/мережі, які взагалі не мають сенсу перевіряти (напр. loopback, link-local, приватні docker-мережі).
- **permanentBlock** — дропаються одразу і безумовно, ще до перевірки trusted/ignore.

Ці три сети (і v6-варіанти) — ДУБЛЬОВАНІ в `scanDetector` і `srvProtector`
з ідентичним вмістом (детальніше — у "Як це працює" вище). Керування —
через `scan-detect-tool`, і кожна команда живого редагування застосовує
зміну в ОБИДВІ таблиці одразу, щоб вони не розійшлись:

```sh
scan-detect-tool --add-trusted 176.104.57.1
scan-detect-tool --add-ignore 10.3.2.0/24
scan-detect-tool --add-permanent 185.177.72.0/24
scan-detect-tool --list 185.177.72.5
scan-detect-tool --show                              # повний дамп ОБОХ таблиць
scan-detect-tool --delete 185.177.72.5
scan-detect-tool --dry-run --add-trusted 192.0.2.1   # показати dry-run, нічого не змінюючи
```

Кожна команда одразу міняє живий сет через `nft` (в обох таблицях) **і**
відповідний override-файл у `/etc/nft-scandetect/` (спільний для обох):

| Список | Override-файл (IPv4) | Override-файл (IPv6) |
|---|---|---|
| trusted | `trusted-extra.list` | `trusted6-extra.list` |
| ignore | `ignore-extra.list` | `ignore6-extra.list` |
| permanentBlock | `permanent-extra.list` | `permanent6-extra.list` |

Якщо такого файлу ще нема — він бутстрапиться поточним станом живого сету
(щоб заводські дефолти з `nft-scan-detector` не загубились), а надалі саме файл
є джерелом правди: під час наступної повної перегенерації (`nft-scan-detector`)
його вміст **повністю замінює** заводські дефолти для цього списку (не merge).

будь-який із цих рестартів. Незалежні srv-таблиці з власними
`rate`/`burst`/`over`/`srv_ports` per-група — підкаталоги
`/etc/nft-scandetect/` (розділ "Назва nft-таблиць" вище). Запланованих,
але нереалізованих ідей наразі нема.

### Підроблена (spoofed) адреса джерела — увімкніть `rp_filter`

Це не баг цього проєкту, а межа самого підходу, і її варто розуміти
явно. Детектор рахує джерела за `ip saddr` **на момент SYN**, тобто ще до
того, як TCP-рукостискання підтвердило, що адреса справжня. Отже,
надіславши SYN із підробленою адресою, зловмисник може:

- **загнати в блок чужу, ні в чому не винну адресу** — включно з тими, чия
  недоступність болить (crawler пошуковика, CDN, партнерський API). У
  `scan` це, нагадаємо, 31 день;
- **засмітити сети** — вони оголошені на 65535 елементів, і заповнити їх
  потоком випадкових адрес нескладно; після переповнення нові (справжні!)
  порушники вже не додаються.

Замінити `ct state new` на "рахувати лише підтверджені з'єднання"
(`ct status assured`) — **не варіант**, перевірено наживо: `assured`
матчить КОЖЕН пакет установленого потоку, а не одну подію на з'єднання
(13 спрацювань замість 1 на звичайнісінькій сесії з кількома обмінами).
Драбина, побудована на такому лічильнику, прогнала б будь-яку активну
легітимну сесію крізь усі рівні в `scan` за секунди. Деталі виміру —
[TESTS.md](TESTS.md).

Правильна відповідь лежить рівнем нижче — reverse path filtering, тобто
відкидання пакетів, чия адреса джерела не маршрутизується назад через той
самий інтерфейс. Це відсікає спуфінг ще до того, як пакет дійде до наших
правил:

```sh
# перевірити поточний стан (1 = strict, 2 = loose, 0 = вимкнено)
sysctl net.ipv4.conf.all.rp_filter net.ipv4.conf.default.rp_filter

# увімкнути (strict підходить типовому хосту з одним аплінком)
echo 'net.ipv4.conf.all.rp_filter = 1'     | sudo tee /etc/sysctl.d/90-rpfilter.conf
echo 'net.ipv4.conf.default.rp_filter = 1' | sudo tee -a /etc/sysctl.d/90-rpfilter.conf
sudo sysctl --system
```

**Обережно з `strict` (1) на асиметричній маршрутизації** — multi-homed
хости, BGP, деякі VPN-топології: там законний трафік може приходити не
тим інтерфейсом, яким пішов би відповідь, і `strict` його відкине. Для
таких випадків — `2` (loose): перевіряє лише, що адреса взагалі
маршрутизована хоч кудись. На типовому одноаплінковому сервері (і на
хостах з docker-мережами) `1` безпечний.
